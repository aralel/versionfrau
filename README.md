# VersionFrau

A Gradle plugin that automatically manages version numbers for your Android (or JVM) project using a `version.properties` file.

- **Debug build** (`assembleDebug` / `bundleDebug`) → increments **build** version
- **Release build** (`assembleRelease` / `bundleRelease`) → increments **patch** version (resets build to 0)

## Setup

### 1. Add JitPack repository

In your root `settings.gradle.kts`:

```kotlin
pluginManagement {
    repositories {
        maven { url = uri("https://jitpack.io") }
        gradlePluginPortal()
        google()
        mavenCentral()
    }
    resolutionStrategy {
        eachPlugin {
            if (requested.id.id == "com.aralel.versionfrau") {
                useModule("com.github.aralel:versionfrau:${requested.version}")
            }
        }
    }
}
```

### 2. Apply the plugin

In your app-level `build.gradle.kts`:

```kotlin
plugins {
    id("com.aralel.versionfrau") version "1.0.0"
}
```

### 3. Use version values

```kotlin
android {
    defaultConfig {
        versionCode = versionFrau.versionCode
        versionName = versionFrau.versionName
    }
}
```

That's it. Two lines of config in `defaultConfig`.

## How It Works

A `version.properties` file is created in your project root:

```properties
major=1
minor=0
patch=0
build=0
```

| Build type | What happens | Output filename |
|---|---|---|
| `./gradlew assembleDebug` | `build` incremented | `app-debug-v1.0.3.42.apk` |
| `./gradlew bundleDebug` | `build` incremented | `app-debug-v1.0.3.42.aab` |
| `./gradlew assembleRelease` | `patch` incremented, `build` reset to 0 | `app-release-v1.0.4.apk` |
| `./gradlew bundleRelease` | `patch` incremented, `build` reset to 0 | `app-release-v1.0.4.aab` |

APKs and AABs are **generated with the versioned name** — AGP writes the file under its final
name directly, so nothing is renamed afterwards and older files in the output directory are never
touched. The version inside the APK/AAB (`versionName` / `versionCode`) is the same version that
appears in the file name. No extra tasks or wiring needed.

> If a future AGP version changes the internals used for naming, VersionFrau falls back to
> renaming — and then only renames files produced by the current build.

### Product flavors

Flavored builds are fully supported. Each variant's outputs are named independently,
keeping the flavor in the filename:

| Command | Generated outputs |
|---|---|
| `./gradlew assembleFreeDebug` | `app-free-debug-v1.0.3.42.apk` |
| `./gradlew assembleDebug` (all flavors) | `app-free-debug-v1.0.3.42.apk`, `app-paid-debug-v1.0.3.42.apk` |
| `./gradlew bundleFreeRelease` | `app-free-release-v1.0.4.aab` |

The version is incremented **once per build**, no matter how many flavors are assembled.
ABI-split APKs all get the version suffix and keep their distinguishing names.

Projects **with and without** flavors work with the same setup — nothing to configure.
Multiple flavor dimensions (e.g. `freeProd`) are supported, and adding or removing
flavors later is safe: leftover outputs from the previous layout are never touched.
When debug and release variants are built in one invocation, all increments run first,
so every output carries the same final version; debug variants still embed and are named with
the four-part version (e.g. `1.0.4.0`), release variants with the three-part one (`1.0.4`).

## Extension Properties

| Property | Type | Debug example | Release example | Description |
|---|---|---|---|---|
| `versionFrau.major` | `Int` | `1` | `1` | Major version |
| `versionFrau.minor` | `Int` | `0` | `0` | Minor version |
| `versionFrau.patch` | `Int` | `3` | `3` | Patch version |
| `versionFrau.build` | `Int` | `42` | `0` | Build version (reset to 0 on release) |
| `versionFrau.versionName` | `String` | `"1.0.3.42"` | `"1.0.3"` | Includes build only on debug |
| `versionFrau.versionCode` | `Int` | `1000342` | `1000300` | Includes build only on debug |
| `versionFrau.fullVersionName` | `String` | `"1.0.3.42"` | `"1.0.3.42"` | Always includes build |
| `versionFrau.buildTime` | `String` | `"Mar 19, 2026"` | `"Mar 19, 2026"` | Current build timestamp |

> **Note:** `versionName`, `versionCode` and `fullVersionName` are build-type-aware and are
> resolved at configuration time by inspecting the Gradle start parameters — no extra code needed.
> They already include the increment the build is about to perform (e.g. `assembleDebug` with
> `build=41` on disk yields `1.0.3.42`), so the app's embedded version matches the file name and
> `version.properties` after the build. `major` / `minor` / `patch` / `build` return the raw values
> currently on disk.

### BUILD_TIME

A `BUILD_TIME` field is automatically injected into every Android `BuildConfig`:

```java
// Auto-generated by VersionFrau
public static final String BUILD_TIME = "Mar 19, 2026";
```

Access it in your code via `BuildConfig.BUILD_TIME`.

## Manual Tasks

You can also run version bumps manually:

```bash
./gradlew incrementBuildVersion
./gradlew incrementPatchVersion
./gradlew incrementMinorVersion   # resets patch & build
./gradlew incrementMajorVersion   # resets minor, patch & build
```

## Custom Version File Location

```kotlin
versionFrau {
    versionFile = file("config/version.properties")
}
```

## Publishing (maintainers)

The easiest way is the script, which sets up `~/.gradle/gradle.properties` from your GPG key and publishes:

```bash
scripts/publish.sh --local-only   # set up + verify signatures, no upload
scripts/publish.sh                # upload; release in the Central Portal
scripts/publish.sh --release      # upload and release automatically
```

Manual setup:

Credentials live in `~/.gradle/gradle.properties` (never in the repo):

```properties
mavenCentralUsername=<Central Portal token username>
mavenCentralPassword=<Central Portal token password>
signingInMemoryKeyId=<last 8 characters of the GPG key id>
signingInMemoryKey=<armored private key on ONE line, without -----BEGIN/END----- lines and without the trailing =XXXX checksum>
signingInMemoryKeyPassword=<GPG passphrase>
```

`.properties` files have no end-of-line comments: put comments on their own line, or they become part of the value.
Publishing to Maven Central and signing are switched on in the project's `gradle.properties` (`mavenCentralPublishing=true`, `signAllPublications=true`).

```bash
./gradlew publishToMavenLocal          # dry run: check the .asc signatures in ~/.m2
./gradlew publishToMavenCentral        # upload; then release the deployment in the Central Portal
```
